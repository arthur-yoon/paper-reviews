# Constrained Entity Selection under Partial Knowledge for LLM-Based Knowledge Graph QA

## 핵심 아이디어 한 줄 요약
LLM이 생성한 지식 그래프(QA) 답변 후보를, 질문에서 추출한 가벼운 기호적 제약(유형, 관계, 제외 조건)으로 검증하여 오답을 걸러내고 정답의 신뢰도를 높이는 'CES-PK(부분 지식 하에서의 제약적 엔티티 선택)' 프레임워크를 제안한다.

## 구현 설명
이 논문의 핵심은 '완전한 쿼리 생성' 대신 '후보 검증'에 초점을 맞춘다는 점이다. 기존 방식이 LLM에게 SPARQL 같은 실행 가능한 쿼리를 만들게 하거나(복잡하고 깨지기 쉬움), 단순히 추론만 하게 두는 것(보장 없음)과 달리, CES-PK는 다음과 같은 3단계 구조로 동작한다.

1.  **후보 생성 (LLM 기반):**
    질문을 LLM에 입력하면, 그래프에 존재할 수 있는 '엔티티(개체)' 후보 목록을 출력받는다. 이때 LLM은 정확한 답을 보장하지 않으며, 가능한 답들을 나열한다.

2.  **제약 추출 (기호적 파싱):**
    질문 문장에서 LLM의 추론 과정 없이도 추출할 수 있는 '경량 제약'들을 정의한다.
    *   **유형(Type) 제약:** "X의 종류는?"이라는 질문에는 X가 특정 유형(예: 단백질, 질병)이어야 한다는 조건.
    *   **관계(Relation) 제약:** "A가 B와 어떤 관계인가?"라는 질문에는 A와 B 사이에 특정 관계(예: 상호작용, 원인)가 존재해야 한다는 조건.
    *   **제외(Exclusion) 제약:** "A와 B는 다르다", "C는 포함되지 않는다"와 같은 부정적 조건.

3.  **부분 지식 하에서의 검증 (3-값 논리 적용):**
    지식 그래프(KG)는 현실과 달리 정보가 불완전하다(Open-world assumption). 따라서 단순히 '조건이 맞지 않으면 거짓'이라고 판단하는 2-값 논리(True/False)를 쓰면, 그래프에 정보가 없어서 모른다고 하는 경우까지 오답으로 처리하게 된다.
    *   **Satisfied (충족):** 그래프 데이터로 확실히 제약이 맞는 것을 확인함. → **정답 후보로 상향 평가**.
    *   **Violated (위반):** 그래프 데이터로 확실히 제약이 맞지 않음을 확인함(예: '질병'을 묻는데 후보가 '단백질'임이 확증됨). → **오답으로 제거**.
    *   **Unknown (미확인):** 그래프에 해당 정보가 없어서 판단 불가. → **보류(Recall 유지)**.

**개념적 예시:**
질문: "알츠하이머병과 관련된 단백질은?"
*   LLM 후보: [Protein_A, Disease_B, Protein_C, Unknown_D]
*   추출된 제약: 후보는 '단백질' 유형이어야 한다.
*   검증 과정:
    *   Protein_A: 그래프에서 Protein_A가 '단백질'임이 확인됨 → **Satisfied**.
    *   Disease_B: 그래프에서 Disease_B가 '질병'임이 확인됨 → **Violated** (제거).
    *   Protein_C: 그래프에 유형 정보가 없음 → **Unknown** (보류).
    *   Unknown_D: 그래프에 아예 없는 엔티티 또는 정보 없음 → **Unknown** (보류).
*   최종 결과: Disease_B는 제거되고, Protein_A는 '충족'이라는 긍정적 증거로 상위 랭킹에, Protein_C/Unknown_D는 하위 랭킹이나 보류 상태로 남는다.

```mermaid
flowchart TD
    A[질문 입력] --> B(LLM 기반 후보 엔티티 생성)
    A --> C(경량 기호 제약 추출: 유형/관계/제외)
    B --> D{제약 검증 엔진}
    C --> D
    D --> E{그래프 데이터 조회}
    E --> F{3-값 평가}
    F -- Satisfied --> G[정답 후보 유지 및 순위 상향]
    F -- Violated --> H[오답 제거]
    F -- Unknown --> I[후보 보류 (Recall 유지)]
    G --> J[최종 정답 목록 출력]
    I --> J
```

## 실행 방법과 예상 출력
Hetionet(생의학 지식 그래프)를 대상으로 실행한다고 가정할 때, 다음과 같이 진행되며 출력이 생성된다.

**실행 시나리오:**
1.  **데이터 준비:** Hetionet에서 엔티티(단백질, 질병, 약물 등)와 관계(상호작용, 부작용 등) 데이터를 로드한다.
2.  **질문 생성:** "시타클로프빈(Cytarabine)이 유발하는 주요 부작용은?" 같은 질문을 구성한다.
3.  **LLM 호출:** LLM에게 이 질문을 주고, Hetionet에 존재할 수 있는 '질병' 또는 '증상' 엔티티 ID 목록을 요청한다.
    *   LLM 출력 예: `[Leukopenia, Nausea, Hepatotoxicity, Protein_X]`
4.  **제약 추출:**
    *   유형 제약: 후보는 '질병/증상' 유형이어야 함.
    *   관계 제약: 'Cytarabine'과 'side_effect' 관계가 있어야 함.
5.  **검증 및 필터링:**
    *   `Leukopenia`: Hetionet에서 'Cytarabine' -> 'side_effect' -> 'Leukopenia'가 확인됨 → **Satisfied**.
    *   `Nausea`: Hetionet에서 'Cytarabine' -> 'side_effect' -> 'Nausea'가 확인됨 → **Satisfied**.
    *   `Hepatotoxicity`: Hetionet에서 'Cytarabine'과 'Hepatotoxicity'의 연결이 없거나, 다른 약물과의 연결만 있음 → **Violated** 또는 **Unknown** (데이터에 따라 다름. 만약 확실히 다른 약물이 원인임을 알면 Violated).
    *   `Protein_X`: '단백질' 유형임이 확인되면 '질병/증상' 제약과 충돌 → **Violated** (제거).

**예상 출력 지표 변화:**
*   **정밀도(Precision) 향상:** `Protein_X`와 같은 유형이 다른 엔티티, 또는 관계가 없는 엔티티가 `Violated`로 제거되므로, 최종 목록에 들어오는 답변의 정확도가 높아진다.
*   **환원율(Recall) 유지:** `Leukopenia`나 `Nausea`처럼 LLM이 제안했지만, 그래프에 명확한 '부작용' 관계가 기록되지 않아 **Unknown**으로 분류된 후보들이 제거되지 않고 목록에 남으므로, 실제 정답일 수 있는 후보가 실수로 뚝 끊겨서 사라지는 현상을 막는다.
*   **랭킹 개선:** **Satisfied** 상태인 엔티티(확실히 관계가 증명된 것)가 **Unknown** 상태인 엔티티보다 높은 점수(상위 랭킹)를 받는다. 즉, "확실한 답"과 "가능성은 있지만 확증은 안 된 답"을 구분하여 제시한다.

## 한계
1.  **제약의 단순성:** 이 프레임워크는 '유형', '직접 연결된 관계', '제외'와 같이 매우 경량적인 제약만 사용할 수 있다. 다단계 추론(예: "A의 B와 관련된 C는?")이나 복합 논리(AND/OR 조합)를 처리하는 능력은 SPARQL 파싱 방식에 비해 제한적일 수 있다. 제약 추출 자체가 LLM에 의존하거나 규칙 기반으로 되어야 하는데, 복잡한 문법 구조를 가진 질문에서는 제약 추출 정확도가 떨어질 수 있다.
2.  **그래프 품질 의존:** 'Unknown' 상태가 많아지면 필터링 효과가 감소한다. 만약 지식 그래프가 매우 불완전하거나, 'Satisfied'로 판단할 수 있는 확증 데이터가 적으면, 이 방법은 정밀도를 높이는 데 큰 도움이 되지 못하고 단순히 '위반'된 것만 걸러내는 수준에 그칠 수 있다.
3.  **부분 지식 처리의 보수성:** 3-값 논리를 사용하여 오답 재거(incorrect rejection)를 막는 대신, 실제 오답일 가능성이 높은 'Unknown' 후보들도 최종 결과물에 포함된다. 이는 환원율은 유지하지만, 사용자가 확인해야 할 노이즈가 증가할 수 있다. 프로덕션 환경에서는 이 'Unknown' 목록을 어떻게 처리할지(예: 추가 검색 트리거, 신뢰도 점수 부여)에 대한 추가적인 UI/UX 또는 후처리 로직이 필요하다.
4.  **실행 가능한 쿼리 미생성:** 이 방법은 최종적으로 SPARQL 쿼리나 다른 프로그래밍 언어 쿼리를 생성하지 않는다. 따라서 LLM의 추론 과정(Chain-of-Thought)을 시각화하거나, 사용자가 쿼리를 수정해 보려는 경우가 많인 인터랙티브 KGQA 시스템에서는 활용에 제약이 있을 수 있다. 오직 '엔티티 목록 필터링' 용도로만 사용 가능하다.
